## 1. 正式回答Fact（2026-11-04受領）
- `POST /v1/organizations`、`PATCH /v1/organizations/{id}` で `sku`（Core/Plus）と `quantity`（割当ライセンス数）を指定できる。Core/Plusの**当該MSP向けSKU実値は後日提供予定**。一括更新APIではプラン変更不可、Organization単位で更新する。
- Organization CSV一括取込みなし。APIを顧客ごとに実行する方式は可能。レート制限は5分2,000要求との回答。請求期間（月次/年次）はMSPアカウント単位で設定される。
- 課金数量はMSP Billing上の保存済みplan/license allocation。実端末数は参考利用状況であり、超過時に自動増枠・超過請求・サービス停止は行われない。割当増減は保存時点で即時適用・日割り精算。
- MSP最低料金は月額150米ドル。親Organizationに個別のライセンス課金なし。社内/検証用NFRは標準25ユーザー、再販売・顧客割当は禁止。
- `DELETE /v1/organizations/{id}` が正式API。事前にRoaming Clientアンインストール、Site撤去、DNS参照先変更が必要。削除後はDNSサービス即停止、設定・ログ等消失、復元不可。日割りクレジットは次回請求。
- 停止状態での無課金保持はできない。アクティブOrganizationは最低1ライセンス。解約/削除後の保持・復元条件については追加回答待ち。
- `GET /v1/invoices` はプラン別請求合計/期間、`GET /v1/metrics/organization_usage/{id}` は利用状況。Organization別確定請求CSV/APIは回答されていない。請求書は画面から個別DL。
- Trialは米国東部時間2026-11-14 23:59 EST終了（日本時間2026-11-15 13:59）。カード登録済みなら自動有料化、未登録なら課金なしで停止。Trial中に有料プランを選ぶと直ちに課金開始。
- 請求締めの正確な時刻/タイムゾーン、Core/Plus SKU実値、解約後保持条件はベンダー追加回答待ち。

## 3. 実装前の必須差分
- 現行`DnsFilterManagementClient.createOrganization(name)`は存在するが、`sku`/`quantity`の設定処理は未確認・未実装。既存APIのrequest body、OpenAPIの必須属性・型・課金開始条件を正式SKU受領後に照合する。
- 現行`POST /admin/dnsfilter/organizations`には作成draft/結果不明時の停止・復旧がある。再利用し、APIタイムアウト時の重複作成・二重課金を避ける。結果不明の自動再POSTは禁止。
- 登録時は課金開始の可能性を確認画面に明示。SKU値が届くまで有料planを含む作成APIを送らない。ライセンス数は非負/上限等のAPI正式制約に合わせて検証し、数量を端末数から勝手に決めない。
- 新規登録とF5同期の競合・並行作成・既存mappingの一意性を既存migration制約で保護。途中成功・失敗・UNKNOWNを分ける。
- ライセンス変更は即時仕入課金へ影響するため、権限/確認/監査を必要最小限で実装。変更後はread-backで実際の保存値を確認する。GETの利用状況を請求確定数量と取り違えない。
- Organization解約削除は既存PR #44/C2の安全ゲートと端末E2Eを再利用。DELETE API存在だけで安全な一括解約完了と判定しない。

## 4A. 2026-11-04 統括修正：DNSFilter APIの薄い管理画面に限定

**最上位原則**：DNSFilterの公式管理画面が正本。Secure Guardは、**DNSFilter APIで事実として取得できる情報の表示と、正式に提供される操作の実行**だけをシンプルにまとめる。自社で推測した端末状態・登録済み判定・稼働台数・保護台数・申告ライセンス数・ライセンス増減算定ロジックを作らない。

- Secure Guardの商品範囲は**Roaming Clientエージェント方式のみ**。Network経由DNS保護、Network Licenseの独自課金管理はサービス対象外。
- `GET /v1/user_agents` が返したAgentレコード2件は**一覧の2件**という事実のみ。そこから「登録済み台数」「保護中台数」「請求台数」という独自の意味付けをしてはならない。APIの`status`/`agent_state`も、管理画面のラベルとの対応が実測で裏付けられない限り独自解釈しない。
- 以前の`P=保護中端末数`・`U=Agent総件数`・`Q=min(C,max(1,P))`などの**派生計数・自動割当の提案は撤回**。数値を独自集計して自動PATCHする処理を作らない。すでに確認済みのDNSFilter側の管理値がAPIで取得・更新できる場合に限り、その値をそのまま利用する。
- APIで取得できない`Allocated RC Licenses`、ライセンス使用数、Protected端末数をSecure Guard内に再構成して表示・保存することはしない。取得不能なら「取得不可／DNSFilter管理画面で確認」と扱う。画面上で推定した0件も禁止。
- Organization/Site/Agent等の既存API連携・顧客別Scope・認証・監査・結果不明時の停止・F5同期は継続。DNSFilterが提供しない業務管理システムを新設しない。
- Organization作成時のCore/Plus SKU値は正式連絡待ち。割当数量PATCHや課金調整は公式APIによる**取得と変更後確認**が可能になるまで自動化しない。未確認の更新・課金操作は行わない。
- 「運用を煩雑にしない」「契約を超える仕入を避ける」は維持すべき事業要件。ただしAPIの根拠なく自動台数補正を作ることで達成したことにはしない。APIで不可能な操作はDNSFilter公式管理画面へ誘導する。

この節は本Decisionや周辺実装契約にある**保護数の独自計算、Agentレコード数の転用、自動数量調整の案より優先**する。

## 4B. 最新承認方針：割当数だけ契約時・変更時に手動転記（2026-11-04）

- **DNSFilterの公式管理画面が正本**という原則は変えない。APIから`Allocated RC Licenses`が取得できない場合は、atLIBの`msp_admin`が**契約開始時とDNSFilter側の割当変更時だけ**、公式画面に表示される割当数をSecure Guardへ手入力する。
- この入力値はDNSFilterの申告割当を照合するための**参照用控え**であって、Secure Guardが新しく決定した契約台数・実端末数・課金数ではない。GUIと異なる場合は**公式画面を正として手動で更新**する。入力更新日時・更新者を既存監査に記録し、参照値である旨を明示する。
- 実際の利用状況は**これまでのPoC・既存実装で確認したDNSFilter APIの情報**を定期的に取得する。Agentレコード数を独自計数して保護台数とみなす機能は作らない。必要なAPIの取得フィールド／データスコープは既存検証記録に合わせる。
- シンプルな超過監視：**APIが提供する利用台数 > 手動入力された割当ライセンス数**であれば顧客の管理者へ是正依頼通知。超過なしは何もしない。同じ超過状態を通知し続けないための最小の通知履歴は可。割当数が未入力、API利用数が取得不能、古い/不明の場合は推定せず`UNKNOWN`扱いとして通知・課金の誤判定を避ける。
- 割当数の自動PATCH、自動増減、独自Agent状態管理、Networkライセンス集計、複雑な契約台数マスタは本方針では不要。DNSFilter公式画面で割当を変更した後に参照値を更新する、という**変更時だけの手作業**でよい。
- 通常画面は顧客別に**DNSFilter利用数／転記した割当数／超過有無／最終確認日時**のみ表示（APIで利用数が取得できることが前提）。参照値をDNSFilterのAPI取得値と偽って表示しない。
- **手動入力値はDNSFilter本体の設定を変更しない**。顧客の契約上限とDNSFilterの割当が別に存在する場合は混同しない。課金額が契約上限を超えないことまでこの通知だけで保証できると誤認しない。

本節は4Aの「APIから取得できない割当数は保存しない」という記述のみを例外として更新し、**ユーザー承認の明示的な手動転記**を認める。独自に台数・状態を算出しない原則は維持する。

## 4C. 超過通知の配信先を管理画面＋Slackに確定（2026-11-04）

- 超過状態はSecure Guardの管理画面に表示し、**同時にSlackの指定チャンネルにも通知する**。表示と通知は同一の超過判定結果を使い、別々に台数を算定しない。
- 通知内容は最小限：顧客名、DNSFilter APIから取得した利用数、DNSFilter管理画面から手動転記した割当数、超過台数、確認日時、Secure Guard管理画面への参照導線（有効なURLがある場合のみ）。APIの原データを独自のAgent「登録台数」等に置換しない。
- **Slackのチャンネルは実装時にユーザーが指定する。現時点では未確定。** 未指定なのに既存の顧客申込用・月次レポート用のSlack Webhookへ流用・送信しない。Secure Guard用通知先を独立の設定として扱い、設定されるまでSlack送信を行わない。設定後、実際の送信試験は別途確認する。
- 既存`src/config.ts`にSlack Incoming Webhookの設定枠（顧客申込・月次レポート）があるため、**送信機構・秘密情報取扱いの既存パターンを再利用**する。新たなSlackアプリ開発、複雑な通知先マスタ、顧客ごとのSlack連携は追加しない。
- 同じ超過状態での定期実行ごとの重複通知を防ぐ。新規超過・超過数の変化など、意味のある変化に限って送信する。最小限の通知履歴だけ保持する。正常・UNKNOWNを「超過解消」と誤認して誤通知しない。
- Slackが未設定・送信失敗の場合でも、管理画面側の超過表示は継続。送信成功と判定できない状況で「通知済み」として記録しない。Webhook URLやToken、認証情報をログに出さない。
- 通知の前提条件は従来どおり**既存PoC・実装で確認済みの公式利用数が取得できること**と、MSP管理者による割当数の手動転記があること。独自の台数集計・DNSFilter自動PATCHは行わない。
