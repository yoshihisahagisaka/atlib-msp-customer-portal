## 手順0: 前提プロセス（参照のみ・本ドキュメントの対象外）

以下は本ドキュメントが扱う技術的オンボーディングの**前提として完了しているべき**業務プロセスであり、実施自体は別プロセス（サービスLP・申込みフォームは今後別途作成予定）。

```
①申込みフォーム送信
  ↓
②ヒアリング日程調整
  ↓
③Web会議でatLIB担当者が顧客のネットワーク環境・監視対象機器台数を確認し、プランを確定
  ↓
④（本ドキュメントの手順1へ）
```

③の完了時点で、以下が確定していることを前提に手順1以降を進める。

| 項目 | 用途 |
|---|---|
| `customer_code`（英数字ID） | ポータルDB・Zabbixオブジェクトの内部キー。**命名規則: `atlse`＋6桁ゼロ埋め連番**（`atlse000001`、`atlse000002`…）。自分で決めるのではなく、Sensor Edge機器管理台帳の「顧客マスタ」タブであらかじめ予約されているIDの中から次の未割当のものを使う（下記参照） |
| `company_name`（正式名称） | Zabbixホストグループ表示名（例: `atLIB株式会社様`） |
| 連絡先メールアドレス | 初回パスワード通知メールの送信先 |
| プラン名 | 契約管理・顧客への案内用（例: `エントリープラン`）。Zabbix側の構成には使用しない（2026-07-22廃止。旧仕様は変更履歴を参照） |
| ネットワーク環境情報（IPレンジ） | 手順3のディスカバリルール作成に使用 |
| SNMP監視対象機器のおおよその台数 | **50台を上限の目安とする**（詳細は`Sensor Edge/運用手順書_顧客追加フロー.md`の「監視対象機器の上限」を参照）。超過見込みの場合は標準構成（Raspberry Pi 5/1GB）ではなく上位RAMモデル・機材追加を個別見積りとして検討する |

**手順1に進む前に**：Sensor Edge機器管理台帳（[スプレッドシート](https://docs.google.com/spreadsheets/d/1x5dtPGwh-AqJamPmKA8TTj40D9noYWancf7WipK5I4E/edit)、`Sensor Edge/運用手順書_機器管理システム.md`参照）の「顧客マスタ」タブを開き、「顧客名」欄が**空欄**になっている行から次の1件を選ぶ（独立したステータス列は無く、空欄＝未割当・記入済み＝割当済みを兼ねる。2026-07-21訂正）。その行の「顧客ID」の値がそのまま`customer_code`になる。「顧客名」欄に`company_name`を記入する。手順1（Sensor Edge設置、機器登録フォームへの入力を含む）が手順2（ポータルオンボーディングスクリプト実行）より先に行われるため、機器登録フォームの顧客IDプルダウンに選択肢が出るよう、この時点で割当を済ませておく必要がある（手順2まで待つと順序が逆転し、機器登録フォームが使えない）。

## 手順1: Sensor Edge設置・Zabbix Proxy登録（全顧客必須）

**MSPサービスとして「リモート監視・運用」を提供する以上、監視対象がインターネットから直接到達可能かどうかに関わらず、Sensor Edgeは全顧客に対して必ず設置する。**「Sensor Edgeが必要かどうか」の判断は不要（条件分岐なし）。

具体的な作業手順（ゴールデンイメージ作成、GCPリレーサーバーでの顧客払い出し、ラズパイへの設定投入、Zabbix Serverへのホスト登録、発送、疎通確認）は `Sensor Edge\運用手順書_顧客追加フロー.md` の手順1〜9をそのまま参照する（重複記載しない）。

**完了条件（次の手順に進む前に必ず確認）**：
- Zabbix管理画面で当該Proxyが「使用可能（Available）」表示になっていること
- 発行された **`proxyid`**（Zabbix Proxy ID）を控えていること（手順2で使用する）

> **順序制約（重要）**：`msp-customer-portal`のDBスキーマ上、`zabbix_proxy_id`は顧客レコード作成時にのみ設定でき、後から更新する手段がコード上用意されていない。そのため、**必ず本手順を完了させてから手順2のオンボーディングスクリプトを実行すること**。逆順で実行してしまった場合、現状は手動でのDB編集以外に是正手段がない。

## 手順2: ポータルオンボーディングスクリプト実行

**実行環境（2026-07-21セットアップ済み）**: `msp-frontend-server`にSSHして実行する。

```bash
gcloud compute ssh msp-frontend-server --zone=asia-northeast1-a --tunnel-through-iap
cd /opt/atlib-msp-dev/msp-customer-portal
```

このサーバーには以下がセットアップ済み：
- `git sparse-checkout`に`msp-customer-portal`を追加済み、`npm install`済み
- 本番のSecret Managerから取得した認証情報一式（DB・Zabbix API・SMTP・JWT・管理画面Basic認証）を`.env`に生成済み（`.env`自体はgit管理外。**`chmod 644`**でこのサーバー上にのみ存在。当初`chmod 600`にしていたが、`/opt/atlib-msp-dev`はGoogleアカウントごとに異なるLinuxユーザーとして扱われるため、作成者以外が`Permission denied`になる問題が判明し644に変更した。詳細は「複数メンバーでの利用に関する既知の注意点」を参照）
- Cloud SQL Auth Proxy（`cloud-sql-proxy.service`、systemd常駐）が`127.0.0.1:5432`で待受し、本番ポータルDBへ接続

**注意**: このリポジトリは`dotenv`等の`.env`自動読込みの仕組みを持たないため、`npm run onboard`は内部で`node --env-file=.env`を使うよう修正済み（`package.json`参照）。`.env`が存在しない・読み込めない場合は`PASSWORD_RESET_URL_BASE`等の必須値エラーで即座に失敗する。

**`git pull`で`fatal: detected dubious ownership`エラーが出た場合**: 自分のLinuxユーザーで初めてこのリポジトリを操作する時に発生する（`/opt/atlib-msp-dev`の所有者が別ユーザーのため）。以下を一度実行すれば以降は発生しない（**ユーザーごとに1回必要**）。
```bash
git config --global --add safe.directory /opt/atlib-msp-dev
```

```bash
npm run onboard -- \
  --code <customer_code> \
  --name "<company_name>" \
  --email <連絡先メールアドレス> \
  --proxy-id <手順1で控えたproxyid> \
  --ip-range <手順0で確認した顧客のネットワークレンジ、例: 192.168.1.1-254>
```

自動的に以下が実行される（`scripts/onboarding/create_customer.ts`）。

1. ホストグループ作成（`MSP/{company_name}`のみ。プラン別サブグループは2026-07-22に廃止 — 作成されるだけで機器が入らない未使用の空グループになっていたため）
2. 通知用Zabbixユーザー作成（`notify_{customer_code}`）
3. 顧客専用アクション作成（`{customer_code}_alert`）
4. DBへのレコード登録（`zabbix_proxy_id`含む）
5. 初回パスワード通知メールの送信

`customer_code`の重複は自動チェックされ、既に登録済みの場合はエラーで停止する（二重登録防止・実装済み）。

実行完了時、コンソールに**手順3でそのまま使う`setup_discovery.py`のコマンド**が表示される（`--ip-range`を指定していれば埋め込み済み、未指定なら手順3実行前に手で埋める）。

**確認**：手順0の時点で「顧客マスタ」タブへの登録を済ませているはずだが、まだの場合はここで必ず行う（自動連携はしていないため手動。登録が漏れるとSensor Edge機器登録フォームの顧客IDプルダウンに新顧客が出てこない）。

## 手順3: ディスカバリルール・アクションのセットアップ

顧客の機器自動検出は、顧客ごとに個別のディスカバリルール（`MSP_インフラ自動検知_{customer_code}`）を作成する方式。以前は全顧客共通のルール「ユーザー用インフラ自動判別」を使っていたが、テスト運用の混乱を経て2026-07-09に顧客ごとの複製方式へ移行済み（詳細は`zabbixserver/batch/setup_discovery.py`のdocstringを参照）。

手順2の完了時に表示されたコマンドを、`msp-frontend-server`にSSHしてそのまま実行する。**`python`ではなく`python3`**（このサーバーに`python`という実行ファイル名は存在しない。2026-07-22実機で`command not found`を確認・修正）。

```bash
gcloud compute ssh msp-frontend-server --zone=asia-northeast1-a --tunnel-through-iap
cd /opt/atlib-msp-dev/zabbixserver/batch
source ~/zabbix_env.sh   # なければ下記「接続情報の準備」を先に実施
python3 setup_discovery.py --dry-run --customer-code <code> --company-name "<name>"   # まず内容確認
python3 setup_discovery.py --apply ...   # 手順2の出力をそのまま貼り付け（python3に読み替える）
```

**注意（Cloud Runからは実行できない）**：本手順はmsp-customer-portalの本番実行環境（Cloud Run）からは実行できない。Pythonが搭載されておらず、Zabbixサーバーへの直接到達性もない（VPC内部からのみ到達可能）ため。

### 接続情報の準備（`ZABBIX_URL`未設定エラーが出た場合、ユーザーごとに1回）

`setup_discovery.py`は`ZABBIX_URL`・`ZABBIX_USER`・`ZABBIX_PASSWORD`という環境変数を読む設計だが、これらを自動で設定する仕組みが無いため、初めて実行するユーザーは以下のように自分のホームディレクトリに一度だけ作成する（`/opt/atlib-msp-dev`配下は他ユーザー所有のため書き込めない）。

```bash
cat > ~/zabbix_env.sh << 'ENVEOF'
export ZABBIX_URL="https://zabbix.atlib.jp/api_jsonrpc.php"
export ZABBIX_USER="$(gcloud secrets versions access latest --secret=portal-zabbix-user --project=msp-zabbix)"
export ZABBIX_PASSWORD="$(gcloud secrets versions access latest --secret=portal-zabbix-password --project=msp-zabbix)"
ENVEOF
chmod 600 ~/zabbix_env.sh
```
以降のセッションでは`source ~/zabbix_env.sh`を実行すればよい（新しいSSHセッションを開くたびに再度sourceが必要）。

### 【管理者向け】Zabbix API側の前提条件

**確認事項（`setup_discovery.py`がエラーで止まった場合、まずこの2点を確認する）**:

1. APIサービスアカウント（`msp-customer-portal-svc`）のRoleに`drule.*`のAPIアクセス権限があること（Zabbix管理画面 Administration > Users > Roles の「Access to API」に`drule.get`・`drule.create`・`drule.update`・`drule.delete`が含まれているか）
2. 「テストルール」という名前のDiscovery Ruleが存在し、**削除しないこと**。SNMPチェックが2件（sysName・sysObjectID）設定されていること
3. `--proxy-id`に指定するのは**この顧客専用のProxy ID**であること（他の顧客が既に使っているProxy IDを誤って指定しないこと）

「テストルール」のSNMPチェック件数、および`--proxy-id`の他顧客との重複は、どちらも`setup_discovery.py`側で自動チェックされる（それぞれ2026-07-22・2026-07-23追加）。問題があればエラーで停止し、不完全な内容での作成やホストの相乗りを防ぐ。

<details>
<summary>背景（なぜこの3点が必要か）</summary>

- **`drule.*`権限**: 含まれていない場合、`[エラー] No permissions to call "drule.get"`のような形で失敗する。
- **「テストルール」**: 実際にディスカバリを行うルールではなく、**新規顧客のルールを作成する際にSNMPチェック構成（コミュニティ文字列・OID）を複製するための「複製元テンプレート」**としてのみ使われる（`setup_discovery.py`の`SOURCE_RULE_NAME`定数を参照）。無効化された状態で存在するため一見「使われていない古いルール」に見えるが、**削除すると新規顧客のオンボーディングが全件失敗する**（既存顧客の再実行には影響しない）。
- 過去に2回、この前提が崩れて実際に障害になっている：(1) 過去のクリーンアップで誤って削除され、新規オンボーディングが全件失敗（2026-07-22に復旧）。(2) 復旧時にSNMPチェックを1件（sysDescrのみ）でしか復元できず、新規顧客のディスカバリが一部機器（ルーター等、sysDescrには応答しないがsysName/sysObjectIDには応答する機器）を検出できない状態のまま数件のオンボーディングが行われていた（2026-07-22に発覚・修正、atLIBの実運用ルールと同じsysName・sysObjectIDの2件構成に統一）。
- **`--proxy-id`の重複**: 2026-07-23、検証環境で2顧客の discovery rule に同じProxy IDを指定する実験を行ったところ、ZabbixがIP・インターフェース種別・Proxy（ディスカバリ元）の一致を基準に**既存ホストへ新しい顧客のホストグループを追加登録してしまう**ことを確認した。片方の顧客の実機がもう片方の顧客のポータル画面にも表示されてしまう、顧客間のデータ越境事故につながるため、`--proxy-id`は必ずこの顧客専用のものを指定すること。
</details>

<details>
<summary>うまくいかない場合</summary>

- `[エラー] No permissions to call "drule.get"` → 上記1のRole設定を確認する
- `[エラー] 複製元ルール「テストルール」が見つかりません` → 「テストルール」が削除されている。Zabbix管理画面で再作成が必要（SNMPコミュニティ文字列はatLIBの実運用ルール「MSP_インフラ自動検知_atlib」のSNMPチェックからしか復元できないため、担当エンジニアに確認する）

  ```bash
  sudo sed -i 's/^#DNSStubListener=yes/DNSStubListener=no/' /etc/systemd/resolved.conf
  sudo systemctl restart systemd-resolved
  ```
- それ以外の特定の機器だけがディスカバリで検出されない → その機器がどのチェック（SNMP／TCPポート）に応答するか個別に確認が必要。担当エンジニアに相談する

これにより自動的に作成されるもの:
1. ディスカバリルール`MSP_インフラ自動検知_{code}`（ICMP・SNMP・プリンター/サーバー系TCPポートの標準チェックリストで、指定したIPレンジをスキャン）
2. アクション`MSP_SNMP機器登録_{code}`（SNMP応答機器を`MSP/{company_name}`グループへ自動登録）
3. アクション`MSP_ICMPフォールバック登録_{code}`（SNMP非対応機器のフォールバック登録）
4. アクション`MSP_新規機器検知通知_{code}`（新規機器検出時の通知。**作成時は無効状態**。社内(atladmin)向けの動作確認が別途必要。顧客への通知は、顧客がポータルの通知設定ページで「未知機器の検出」トグルを有効化した場合のみ届く）

**完了条件**：`--dry-run`で3つのアクションが「作成済み」と表示されること。

## 手順5: 監視開始の確認

- 手順3のディスカバリルールにより機器が自動登録され、ポータルの「機器管理」画面に一覧表示されることを確認する
- 顧客が自動登録された機器のうち不要なものを、ポータルから無効化・削除できることを案内する

> **注意（削除 vs 無効化）**：ポータルから機器を「削除」しても、その機器が引き続きネットワーク上で稼働している場合、次回のディスカバリサイクルで再度検出・登録される可能性がある（無効化と異なり、削除は「未知の機器」として扱われ直すため）。**恒久的に監視を止めたい場合は、削除ではなく無効化を推奨する**旨を顧客への案内に含める。

## 手順6: 契約終了時のポータル側後処理

Sensor Edge側の機器回収・認証情報失効は`Sensor Edge/運用手順書_顧客追加フロー.md`手順10を参照（Chisel認証情報・Zabbix Proxy PSKの失効はそちらに従う）。本手順は、それと対になる**顧客ポータル側**の後処理を扱う。

### 11-1. ポータルログインを即座に無効化する

`msp-customer-portal`の`customerRepo`には現状、顧客の`status`を更新するAPIエンドポイント・スクリプトが用意されていないため、Cloud SQL Auth Proxy経由でのSQL実行が必要（`msp-customer-portal-db`インスタンス、接続方法は本ドキュメント・過去の障害対応記録を参照。作業前に関係者の承認を得ること）。

```sql
UPDATE customers SET status = 'suspended', updated_at = now() WHERE customer_code = '<対象customer_code>';
```

`findByEmail`/`findById`は`status = 'active'`のみを対象とするため、この更新のみでログイン・API利用が即座にできなくなる（アプリケーションコード側の変更は不要）。

### 11-2. Zabbix側のホストグループ・ホストは即削除せず一定期間保持する

- 契約終了直後は、当該顧客のホストグループに属する全ホストを**無効化**（`host.update`で`status=1`）するに留め、**削除はしない**
- 保持期間（目安1〜3ヶ月、契約内容に応じて調整）経過後、問題なければホストグループごと削除する
- 通知用Zabbixユーザー（`notify_{customer_code}`）・顧客専用アクション（`{customer_code}_alert`、`MSP_新規機器検知通知_{code}`等）も同様に、即削除ではなく無効化を先に行う

### 11-3. データ保持方針

- ポータルDB（`customers`テーブル）のレコード自体は、`suspended`のまま一定期間（Zabbix側と同じ保持期間の目安）保持し、監査・問い合わせ対応に備える
- 保持期間経過後にレコードを削除する場合、`customer_hostgroups`は`ON DELETE CASCADE`で連動削除される（`migrations/001_init.sql`参照）ため、`customers`テーブルの削除のみで両方消える

## トラブルシューティング

### 複数メンバーでの利用に関する既知の注意点（2026-07-22判明）

`/opt/atlib-msp-dev`は、最初にcloneしたユーザーのLinuxアカウントが所有者になっている。**Googleアカウントごとに異なるLinuxユーザー名として扱われる**ため（例: 同じ人物でも`YoshihisaHagisaka`と`yoshihisa_hagisaka`のように別ユーザーになることがある）、自分以外が作成したファイル・ディレクトリに対して`Permission denied`や`git`の`dubious ownership`エラーに遭遇することがある。恒久的な解決（共有グループ化等）は未実施。当面は以下で個別に対処する。

- `git pull`で`fatal: detected dubious ownership`→ `git config --global --add safe.directory /opt/atlib-msp-dev`（ユーザーごとに1回）
- 自分が作成していないファイルへの書き込みで`Permission denied`→ 可能であれば自分のホームディレクトリ（`~/`）に置く運用に変更する（`zabbix_env.sh`はこの方式）

### `npm run onboard` 実行後、顧客がログインできない

- 歓迎メールが迷惑メール判定されていないか確認する
- SMTP送信元（`yoshihisa.hagisaka@atlib.jp`のアプリパスワード経由、暫定運用）の送信制限に達していないか確認する

### 機器管理画面に自動登録された機器が表示されない

- 手順3を実行し忘れていないか（`setup_discovery.py --dry-run`で当該顧客のルール・アクションが作成済みか確認）
- 指定した`--ip-range`が顧客の実際のネットワークレンジと一致しているか確認する
- Zabbix管理画面で、当該顧客のホストグループに実際にホストが追加されているか直接確認する

### `zabbix_proxy_id`を手順1より先に顧客登録してしまった

- 現状、`customerRepo`に更新用メソッドがないため、Cloud SQLへの手動UPDATEが必要になる。実施する場合は関係者の承認を得た上で慎重に行うこと（顧客の実データを直接更新する操作のため）
