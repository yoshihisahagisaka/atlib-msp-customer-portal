# 顧客オンボーディング統合フロー 運用手順書

最終更新: 2026-07-10
関連ドキュメント:
- `Sensor Edge\運用手順書_顧客追加フロー.md`（本手順の手順1で参照する）
- `msp-customer-portal\scripts\onboarding\create_customer.ts`（本手順の手順2で実行する）
- `zabbixserver\batch\setup_discovery.py`（本手順の手順3で実行する）

本ドキュメントは、実顧客のオンボーディングにあたり「申込み確定後」から「監視開始確認」までを1本の時系列手順として整理したものである。`msp-customer-portal`（顧客ポータル）と`Sensor Edge`（顧客拠点設置の物理監視ゲートウェイ）という、これまで別々に運用されていた2つの仕組みをつなぐ位置づけ。

---

## 手順0: 前提プロセス（参照のみ・本ドキュメントの対象外）

以下は本ドキュメントが扱う技術的オンボーディングの**前提として完了しているべき**業務プロセスであり、実施自体は別プロセス（サービスLP・申込みフォームは今後別途作成予定）。

```
①申込みフォーム送信
  ↓
②ヒアリング日程調整
  ↓
③Web会議でatLIB担当者が顧客のネットワーク環境・監視対象機器台数を確認し、プランを確定
  ↓
④（本ドキュメントの手順1へ）
```

③の完了時点で、以下が確定していることを前提に手順1以降を進める。

| 項目 | 用途 |
|---|---|
| `customer_code`（英数字ID） | ポータルDB・Zabbixオブジェクトの内部キー（例: `atlib002`） |
| `company_name`（正式名称） | Zabbixホストグループ表示名（例: `atLIB株式会社様`） |
| 連絡先メールアドレス | 初回パスワード通知メールの送信先 |
| プラン名（複数可） | ホストサブグループ作成に使用（例: `エントリープラン`） |
| ネットワーク環境情報（IPレンジ） | 手順3のディスカバリルール作成に使用 |

## 手順1: Sensor Edge設置・Zabbix Proxy登録（全顧客必須）

**MSPサービスとして「リモート監視・運用」を提供する以上、監視対象がインターネットから直接到達可能かどうかに関わらず、Sensor Edgeは全顧客に対して必ず設置する。**「Sensor Edgeが必要かどうか」の判断は不要（条件分岐なし）。

具体的な作業手順（ゴールデンイメージ作成、GCPリレーサーバーでの顧客払い出し、ラズパイへの設定投入、Zabbix Serverへのホスト登録、発送、疎通確認）は `Sensor Edge\運用手順書_顧客追加フロー.md` の手順1〜9をそのまま参照する（重複記載しない）。

**完了条件（次の手順に進む前に必ず確認）**：
- Zabbix管理画面で当該Proxyが「使用可能（Available）」表示になっていること
- 発行された **`proxy_hostid`** を控えていること（手順2で使用する）

> **順序制約（重要）**：`msp-customer-portal`のDBスキーマ上、`zabbix_proxy_id`は顧客レコード作成時にのみ設定でき、後から更新する手段がコード上用意されていない。そのため、**必ず本手順を完了させてから手順2のオンボーディングスクリプトを実行すること**。逆順で実行してしまった場合、現状は手動でのDB編集以外に是正手段がない。

## 手順2: ポータルオンボーディングスクリプト実行

```bash
npm run onboard -- \
  --code <customer_code> \
  --name "<company_name>" \
  --email <連絡先メールアドレス> \
  [--plan "<プラン名>"]... \
  --proxy-id <手順1で控えたproxy_hostid> \
  --ip-range <手順0で確認した顧客のネットワークレンジ、例: 192.168.1.1-254>
```

自動的に以下が実行される（`scripts/onboarding/create_customer.ts`）。

1. ホストグループ作成（`MSP/{company_name}`、プラン指定があればサブグループも作成）
2. 通知用Zabbixユーザー作成（`notify_{customer_code}`）
3. 顧客専用アクション作成（`{customer_code}_alert`）
4. DBへのレコード登録（`zabbix_proxy_id`含む）
5. 初回パスワード通知メールの送信

`customer_code`の重複は自動チェックされ、既に登録済みの場合はエラーで停止する（二重登録防止・実装済み）。

実行完了時、コンソールに**手順3でそのまま使う`setup_discovery.py`のコマンド**が表示される（`--ip-range`を指定していれば埋め込み済み、未指定なら手順3実行前に手で埋める）。

## 手順3: ディスカバリルール・アクションのセットアップ

顧客の機器自動検出は、顧客ごとに個別のディスカバリルール（`MSP_インフラ自動検知_{customer_code}`）を作成する方式。以前は全顧客共通のルール「ユーザー用インフラ自動判別」を使っていたが、テスト運用の混乱を経て2026-07-09に顧客ごとの複製方式へ移行済み（詳細は`zabbixserver/batch/setup_discovery.py`のdocstringを参照）。

手順2の完了時に表示されたコマンドを、`msp-frontend-server`にSSHしてそのまま実行する。

```bash
gcloud compute ssh msp-frontend-server --zone=asia-northeast1-a --tunnel-through-iap
cd /opt/atlib-msp-dev/zabbixserver/batch
python setup_discovery.py --dry-run --customer-code <code> --company-name "<name>"   # まず内容確認
python setup_discovery.py --apply ...   # 手順2の出力をそのまま貼り付け
```

**注意（Cloud Runからは実行できない）**：本手順はmsp-customer-portalの本番実行環境（Cloud Run）からは実行できない。Pythonが搭載されておらず、Zabbixサーバーへの直接到達性もない（VPC内部からのみ到達可能）ため。

これにより自動的に作成されるもの:
1. ディスカバリルール`MSP_インフラ自動検知_{code}`（ICMP・SNMP・プリンター/サーバー系TCPポートの標準チェックリストで、指定したIPレンジをスキャン）
2. アクション`MSP_SNMP機器登録_{code}`（SNMP応答機器を`MSP/{company_name}`グループへ自動登録）
3. アクション`MSP_ICMPフォールバック登録_{code}`（SNMP非対応機器のフォールバック登録）
4. アクション`MSP_新規機器検知通知_{code}`（新規機器検出時の通知。**作成時は無効状態**。社内(atladmin)向けの動作確認が別途必要。顧客への通知は、顧客がポータルの通知設定ページで「未知機器の検出」トグルを有効化した場合のみ届く）

**完了条件**：`--dry-run`で3つのアクションが「作成済み」と表示されること。

## 手順4: 顧客への引き渡し

- 歓迎メール（手順2で自動送信）が実際に届いていることを確認
- 顧客に初回ログイン手順・パスワード再設定手順を案内する
  - ログインURL: ポータルの `/login.html`
  - パスワードをお忘れの場合は `/reset-password.html` から再設定可能
- 必要であれば、通知設定ページの「未知機器の検出」トグルについても案内する（デフォルト無効）

---

## 手順5: 監視開始の確認

- 手順3のディスカバリルールにより機器が自動登録され、ポータルの「機器管理」画面に一覧表示されることを確認する
- 顧客が自動登録された機器のうち不要なものを、ポータルから無効化・削除できることを案内する

> **注意（削除 vs 無効化）**：ポータルから機器を「削除」しても、その機器が引き続きネットワーク上で稼働している場合、次回のディスカバリサイクルで再度検出・登録される可能性がある（無効化と異なり、削除は「未知の機器」として扱われ直すため）。**恒久的に監視を止めたい場合は、削除ではなく無効化を推奨する**旨を顧客への案内に含める。

## トラブルシューティング

### `npm run onboard` 実行後、顧客がログインできない

- 歓迎メールが迷惑メール判定されていないか確認する
- SMTP送信元（`yoshihisa.hagisaka@atlib.jp`のアプリパスワード経由、暫定運用）の送信制限に達していないか確認する

### 機器管理画面に自動登録された機器が表示されない

- 手順3を実行し忘れていないか（`setup_discovery.py --dry-run`で当該顧客のルール・アクションが作成済みか確認）
- 指定した`--ip-range`が顧客の実際のネットワークレンジと一致しているか確認する
- Zabbix管理画面で、当該顧客のホストグループに実際にホストが追加されているか直接確認する

### `zabbix_proxy_id`を手順1より先に顧客登録してしまった

- 現状、`customerRepo`に更新用メソッドがないため、Cloud SQLへの手動UPDATEが必要になる。実施する場合は関係者の承認を得た上で慎重に行うこと（顧客の実データを直接更新する操作のため）
