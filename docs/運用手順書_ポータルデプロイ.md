## 前提となる構成

- 本体: Cloud Runサービス `msp-customer-portal`（project: `msp-zabbix`、region: `asia-northeast1`）
- コンテナイメージはソースからその都度ビルドされる（`gcloud run deploy --source=.`）。CI/CDパイプラインは無く、開発者のローカル端末から手動デプロイする運用
- DB（`msp-customer-portal-db`、Cloud SQL）へのマイグレーション・オンボーディングスクリプト（`npm run migrate` / `npm run onboard`）は、Cloud Runコンテナ内からではなく、`msp-frontend-server`（GCE VM）にSSHして実行する
  - このVMには`msp-customer-portal`がgit sparse-checkoutで`/opt/atlib-msp-dev/msp-customer-portal`に配置済み、`npm install`済み
  - 本番のSecret Managerから生成した`.env`が同ディレクトリに存在する（git管理外）
  - `cloud-sql-proxy.service`が`127.0.0.1:5432`で常駐し、本番DBへ中継している（追加の起動操作は不要）
- 環境変数の管理は2箇所に分かれている（**手順3で詳述する落とし穴の元**）:
  1. Cloud Runサービス本体（実際にユーザーがアクセスするアプリが読む値）
  2. `msp-frontend-server`上の`.env`（`npm run migrate`/`npm run onboard`を手動実行する時だけ読む値）

## 手順1: 通常のデプロイ（コード変更のみ、DBマイグレーション無し）

1. コード変更をコミット・pushする
2. ローカル端末の`msp-customer-portal`ディレクトリで実行する
   ```bash
   gcloud run deploy msp-customer-portal --source=. --region=asia-northeast1 --project=msp-zabbix
   ```
3. 反映確認
   ```bash
   curl -sk -o /dev/null -w 'HTTP %{http_code}\n' https://msp-customer-portal-135863453696.asia-northeast1.run.app/healthz/
   ```
   （`/healthz`ではなく**末尾スラッシュ付き`/healthz/`**が正しいエンドポイント。理由は「トラブルシューティング」参照）

## 手順2: DBマイグレーションを伴うデプロイ（新しいテーブル・列を追加した場合）

1. コード変更（マイグレーションファイル`migrations/*.sql`含む）をコミット・push
2. `msp-frontend-server`にSSHしてマイグレーションを先に適用する
   ```bash
   gcloud compute ssh msp-frontend-server --zone=asia-northeast1-a --tunnel-through-iap
   cd /opt/atlib-msp-dev
   git pull
   cd msp-customer-portal
   npm install   # package.jsonに変更があった場合のみ必要。無ければスキップ可
   npm run migrate
   ```
3. `config.ts`に新しい必須環境変数（`required(...)`で読むもの）を追加した場合は、ここで**手順3**を先に済ませてから`npm run migrate`を実行する（さもないと`Missing required config value`で即失敗する）
4. マイグレーション成功を確認後、手順1と同様にCloud Runへデプロイする
   ```bash
   gcloud run deploy msp-customer-portal --source=. --region=asia-northeast1 --project=msp-zabbix
   ```

### 標準Runbook: Cloud SQL migration の事前確認・適用・検証

この節を、本リポジトリのCloud SQL migrationの正本とする。参照順序は、(1) この節、(2) `migrations/runner.ts`、(3) 対象migration SQL、(4) `src/config.ts`およびVM上の`.env`である。Cloud Runコンテナ、Cloud Build、手作業のSQL適用はmigration実行経路として使用しない。

#### 実行環境

- 実行場所はGCE VM `msp-frontend-server`。
- VMの`cloud-sql-proxy.service`が`127.0.0.1:5432`からCloud SQL `msp-customer-portal-db`へ中継する。proxyを追加起動しない。
- migration runnerはVM上の`/opt/atlib-msp-dev/msp-customer-portal`にある、対象commitを含むcheckoutから実行する。
- DB接続値は同checkoutのgit管理外`.env`を`node --env-file=.env`で読む。値を表示・Gitへ記録しない。

#### Node.js と依存関係

`migrations/runner.ts`はTypeScriptであり、`npm run migrate`は`ts-node/register`を必要とする。`ts-node`と`typescript`は本リポジトリでは`devDependencies`である。production用コンテナはdevDependenciesを含まないため、コンテナ内からmigrationを実行しない。

VMで`NODE_ENV=production`の場合も、migration実行前に既存checkoutで`ts-node/register`と`typescript`が解決できることを確認する。欠けている場合は、既存運用手順どおり、承認済みの依存関係復旧をVM上のcheckoutに対して実施してから再開する。依存関係が解決できない状態でrunnerを代替スクリプト・手動SQLへ切り替えない。

```bash
node --version
npm --version
node -p "require.resolve('ts-node/register')"
node -p "require('typescript').version"
```

#### 事前確認

```bash
gcloud compute ssh msp-frontend-server --project=msp-zabbix \
  --zone=asia-northeast1-a --tunnel-through-iap

cd /opt/atlib-msp-dev/msp-customer-portal
git status --porcelain
git rev-parse HEAD

set -a; source .env; set +a
PGPASSWORD="$DB_PASSWORD" psql -X -v ON_ERROR_STOP=1 \
  -h "$DB_HOST" -p "$DB_PORT" -U "$DB_USER" -d "$DB_NAME" \
  -c "SELECT filename, applied_at FROM schema_migrations ORDER BY filename;"
```

実行前に、対象SHA、作業ツリーclean、対象SQL、既存ledger、対象migration以外の未適用ファイルがないことを確認する。`runner.ts`はファイル名順に全未適用SQLを処理するため、対象以外が未適用なら停止して統括判断を待つ。

#### 標準実行と成功判定

```bash
cd /opt/atlib-msp-dev/msp-customer-portal
npm run migrate
```

runnerは`schema_migrations`を確認し、適用済みファイルを`skip (already applied): ...`としてskipする。対象SQLは単一トランザクションで実行し、成功時だけ`schema_migrations`へ記録する。成功時の出力は、既存migrationにはskip、対象migrationには次の形式を期待する。

```text
skip (already applied): <既存migration>.sql
applying: <対象migration>.sql
  done
```

適用後は、対象filenameがledgerに1件だけあり、対象テーブル・列が存在することを確認する。

```bash
PGPASSWORD="$DB_PASSWORD" psql -X -v ON_ERROR_STOP=1 \
  -h "$DB_HOST" -p "$DB_PORT" -U "$DB_USER" -d "$DB_NAME" \
  -c "SELECT filename, applied_at FROM schema_migrations WHERE filename = '<対象migration>.sql';"
```

#### 失敗時の扱い

runnerが非0で終了、想定外のmigrationを`applying`、DB接続・必須設定・依存関係・ledgerに不一致がある場合は停止する。自動再試行、手動SQL、`schema_migrations`の編集、テーブル削除は行わない。単一migration内のSQL失敗はrunnerがROLLBACKするが、既にcommit済みの過去migrationを巻き戻すものではない。再開は原因を修正し、ledger・対象schema・対象SHAを再確認した統括承認後に限る。

#### プロジェクト間の再利用範囲

`atlib-sales-tools`も同一VM・Cloud SQL Auth Proxy・`schema_migrations`・TypeScript runnerという運用原則を再利用する。一方、DB名、DBユーザー、`.env`、migration一覧、runnerの並列制御・artifact方式はプロジェクト固有である。他プロジェクトのSQL、認証情報、migration runner、Cloud Run設定をPortalへ流用しない。

#### Secure Guard migration 011の現状

対象SHAは`6ec10ad026073ab5b6aace16aedb0d19fb5ff88a`、対象SQLは`011_secure_guard_identity_scope.sql`である。2026-10-27に、本手順の例外として一時ディレクトリ`/tmp/secure-guard-migrate-6ec10ad`から既存runnerを実行し、本番DB `msp_customer_portal`へ011を適用した。Cloud SQL Auth Proxyの接続先は`127.0.0.1:5432`、Node.jsは`20.20.2`、npmは`10.8.2`、TypeScriptは`5.9.3`である。

本番VMの既存作業ツリーがdirtyだったため、既存checkoutを変更しなかった。Windows側で検証済みの固定SHAのGitアーカイブを作成し、IAP経由でVMの一時ディレクトリへ転送・展開した。GitHub認証をVM上で迂回するための手段であり、対象SHA以外のソースを混入させないための措置である。この例外経路は、既存checkoutをcleanにできない場合だけ使用する。

`NODE_ENV=production`ではdevDependenciesが除外され、`ts-node/register`を解決できなかった。対象アーカイブの一時ディレクトリで、`NODE_ENV`とnpmのomit設定をその実行だけ解除し、lockfileに従って開発依存を導入して復旧した。

```bash
cd /tmp/secure-guard-migrate-6ec10ad
env -u NODE_ENV npm_config_omit="" npm ci --include=dev
node -p "require.resolve('ts-node/register')"
node -p "require('typescript').version"
```

既存VM checkoutの`.env`を値を表示せずに環境へ読み込み、同一の`migrations/runner.ts`を実行した。

```bash
cd /tmp/secure-guard-migrate-6ec10ad
set -a
source /opt/atlib-msp-dev/msp-customer-portal/.env
set +a
node -r ts-node/register migrations/runner.ts
```

実行出力では001〜010がすべて`skip (already applied)`となり、011だけが`applying`、続いて`done`となった。ledgerの011適用日時は`2026-10-27 04:20:17.381774+00`であり、新規7テーブルの存在を確認済みである。

次回は、対象SHA、対象SQL、DB接続先だけを置き換え、同じ事前確認・依存関係確認・runner・ledger検証を適用する。対象外migrationの`applying`、依存関係の解決失敗、DB接続先不一致、runner非0終了、ledgerまたは対象schemaの不一致では停止する。自動再実行、手動SQL、ledger編集は行わない。

#### Secure Guard migration 012の成功記録

2026-10-27に、対象SHA `6d9191733e037e73a346f747458eb7b124a73a36` の`012_secure_guard_organization_independence.sql`を本番DBへ適用した。001〜011はすべて`skip (already applied)`、012は`applying`後に`done`となった。ledgerの適用日時は`2026-10-27 11:37:21.765792+00`である。

適用後、`customer_organizations.organization_name`はNOT NULL、`customer_id`はNULL許容となり、`customer_organizations_customer_id_fkey`は存在しないことを確認した。Secure Guard Organizationは0件であり、既存`customers`テーブル・データは変更していない。

WindowsとLinuxのCRLF/LF差異でSQLファイルの生バイトSHA-256が一致しない場合、改行をLFへ正規化して比較する。アーカイブ自体は生バイトSHA-256で照合し、対象SHAから生成したものだけを使用する。改行差異を内容差異と扱わない一方、正規化後ハッシュまたは対象SQL本文が不一致なら停止する。

```bash
# Linux: CRLFをLFへ正規化した内容ハッシュ
tr -d '\r' < migrations/012_secure_guard_organization_independence.sql | sha256sum
```

次回は対象SHA・対象SQL・DB接続先を置き換えた上で、同じ一時アーカイブ、依存関係準備、既存runner、ledger・schema確認を再利用する。既存VM作業ツリーがdirtyな場合は変更せず、固定SHAのアーカイブを一時ディレクトリへ展開する。

## 手順3: 新しい必須環境変数（`config.ts`の`required(...)`）を追加した場合の反映チェックリスト

`src/config.ts`の`loadConfig()`は、`required()`で読んでいる値が1つでも欠けていると**アプリ全体が起動時に例外で落ちる**（該当ルートだけでなく全体障害になる）。新しい必須値を追加したら、以下の**2箇所両方**に反映すること。片方だけ反映して「動いたから大丈夫」と判断しないこと（もう片方は`npm run migrate`/`npm run onboard`を次に手動実行する人が初めて気づく形で失敗する）。

1. **Cloud Runサービス本体**（本番ユーザーが実際にアクセスする側）
   ```bash
   gcloud run services update msp-customer-portal --region=asia-northeast1 --project=msp-zabbix \
     --update-env-vars=<KEY>=<value>
   ```
   秘匿性の高い値（パスワード等）はSecret Manager経由にする（既存の`portal-jwt-secret`等と同じパターン。`src/config.ts`の`resolveSecret()`を参照）。メールアドレス等の非秘匿値は`--update-env-vars`で直接設定してよい。
2. **`msp-frontend-server`上の`.env`**（`npm run migrate`/`npm run onboard`を手動実行する時だけ使う）
   ```bash
   gcloud compute ssh msp-frontend-server --zone=asia-northeast1-a --tunnel-through-iap
   cd /opt/atlib-msp-dev/msp-customer-portal
   grep -q "^<KEY>=" .env || echo "<KEY>=<value>" >> .env
   ```

反映確認: `.env`に登録済みのキー一覧（値は表示しない）
```bash
cut -d= -f1 .env | sort
```
`src/config.ts`の`required(...)`呼び出し一覧と突き合わせて、抜けがないか確認する。

**注意**: `SLACK_WEBHOOK_*`（`config.slack.*`）は`required()`を使っていない**任意項目**なので、このチェックリストの対象外（未設定でもアプリは起動する。Slack通知が送られないだけ）。設定する場合は「1. Cloud Runサービス本体」のみでよく、`msp-frontend-server`上の`.env`（`npm run migrate`/`npm run onboard`用）への追記は不要（これらのスクリプトはSlack通知を送らないため）。

## トラブルシューティング

### `npm run migrate` / `npm run onboard`が`Missing required config value: XXX`で失敗する

`msp-frontend-server`上の`.env`に、その環境変数が登録されていない。手順3の「2. `msp-frontend-server`上の`.env`」を実施する。

**背景**: `.env`はSecret Manager等から自動生成されたものではなく、過去のある時点で一度作成されたきり手動更新が必要なファイル。`config.ts`に必須値を追加しても`.env`側は自動追従しないため、時間が経つほど両者がズレていく。2026-08-03、`CUSTOMER_APPLICATION_NOTIFY_EMAIL`（顧客申込みフォーム機能で追加）と`MONTHLY_REPORT_FROM_EMAIL`（月次レポート機能で追加）の2つが未登録のまま放置されていたことが判明し、追記して解消した。

### ルートURL直下の`/healthz`が404になる

正しいエンドポイントは末尾スラッシュ付きの`/healthz/`（`server.ts`の`app.get('/healthz', ...)`はExpress上は末尾スラッシュ無しにもマッチするはずだが、Cloud RunのURL経由では末尾スラッシュ無しは404になる挙動を2026-08-03に確認済み。原因未特定・実害無し。死活監視（Uptime Check）も`/healthz/`を対象にしている）。

### デプロイ検証時に投入したテストデータが残ってしまった場合

Cloud SQL Auth Proxy経由で直接削除する（`運用手順書_顧客オンボーディング統合フロー.md`手順6-1と同じ接続方法）。
```bash
gcloud compute ssh msp-frontend-server --zone=asia-northeast1-a --tunnel-through-iap
cd /opt/atlib-msp-dev/msp-customer-portal
set -a; source .env; set +a
PGPASSWORD="$DB_PASSWORD" psql -h "$DB_HOST" -p "$DB_PORT" -U "$DB_USER" -d "$DB_NAME" -c "DELETE FROM <table> WHERE <条件>;"
```
