# 実施手順（かんたん版）: 顧客オンボーディング統合フロー

最終更新: 2026-07-24
対応する詳細仕様書: `msp-customer-portal/docs/運用手順書_顧客オンボーディング統合フロー.md`

## これは何の作業か

申込みが確定した顧客を、実際に監視サービスが使える状態にするまでの一連の作業。Sensor Edge（拠点設置の機器）の設置と、顧客ポータル（Webサイト）への登録の両方を行う。

## 始める前に

以下がヒアリング（Web会議）で確定していること。無ければ担当者に確認してから始める。

| 項目 | 例 |
|---|---|
| `customer_code`（英数字ID） | `atlse000003`のような形式（`atlse`＋6桁連番）。自分で決めず、手順0で顧客マスタから割り当てる |
| `company_name`（正式名称） | `atLIB株式会社様` |
| 連絡先メールアドレス | |
| プラン名 | `エントリープラン` |
| 顧客のネットワークのIPレンジ | `192.168.1.1-254` |
| SNMP監視対象機器のおおよその台数 | 50台が目安の上限。超えそうな場合は担当エンジニアに相談 |

また、`msp-frontend-server`にSSH接続できる環境が必要（手順3で使用）。

下記「作業者の初回セットアップ」に該当すれば先に済ませ、その後は手順0〜5を上から順に実施すればよい（顧客が変わっても手順0からやり直すだけで、セットアップの再実施は不要）。エラーが出た場合のみ[うまくいかない場合](xref:guide-onboarding#うまくいかない場合)を参照する。

## 作業者の初回セットアップ（顧客ごとではなく、あなた自身が初めてこの作業をする時に1回だけ）

以下2つは、**あなたが**`msp-frontend-server`**で初めてこの手順3を実行する時に一度だけ**必要（誰かが1回実施済みなら不要。顧客を1件追加するたびにやり直す必要はない）。2回目以降・他の顧客の対応時はこのセクションを読み飛ばして手順0から始めてよい。

### `~/zabbix_env.sh`が無い場合（手順3で使用）

1. **操作**: 以下をそのまま実行する（Secret Managerから直接値を取得するので、パスワードが画面に表示されることはない）
   ```bash
   cat > ~/zabbix_env.sh << 'ENVEOF'
   export ZABBIX_URL="https://zabbix.atlib.jp/api_jsonrpc.php"
   export ZABBIX_USER="$(gcloud secrets versions access latest --secret=portal-zabbix-user --project=msp-zabbix)"
   export ZABBIX_PASSWORD="$(gcloud secrets versions access latest --secret=portal-zabbix-password --project=msp-zabbix)"
   ENVEOF
   chmod 600 ~/zabbix_env.sh
   ```
2. **注意**: 新しいSSHセッションを開くたびに、手順3の3.（`source ~/zabbix_env.sh`）が必要（ファイル自体は再作成不要。これは「セッションを開くたび」に必要な操作であり、上記の「初回セットアップ」には含まれない）

### `git pull`で`fatal: detected dubious ownership`というエラーが出る場合

自分のアカウントで初めてこのリポジトリを操作する時に一度だけ必要。

```bash
git config --global --add safe.directory /opt/atlib-msp-dev
```

## 手順0: 顧客マスタで顧客IDを割り当てる（新規顧客ごとに毎回実施）

1. **画面**: [Sensor Edge 機器管理台帳](https://docs.google.com/spreadsheets/d/1x5dtPGwh-AqJamPmKA8TTj40D9noYWancf7WipK5I4E/edit)を開き、「顧客マスタ」タブを開く
2. **操作**: 「顧客名」欄が**空欄**になっている行のうち、一番上の行を選ぶ（空欄＝未割当の顧客ID）
3. **操作**: その行の「顧客名」欄に会社名（`company_name`）を記入する。連絡先メールアドレス・備考も分かれば記入する
4. **確認**: その行の「顧客ID」の値（例: `atlse000003`）を控える。これが以降の手順で使う`customer_code`になる（「顧客名」欄が埋まった時点でこの顧客IDは割当済み扱いになる。ステータス列は存在しない）
5. **注意**: この手順を飛ばして手順1に進むと、Sensor Edge機器登録フォームの顧客IDプルダウンにこの顧客が出てこず、機器を登録できない

## 手順1: Sensor Edgeの設置（全顧客で必ず実施）

この手順は省略できない。**必ず** `Sensor Edge/実施手順_顧客追加フロー.md` の手順1〜9をそのまま実施する。

**完了条件（次の手順に進む前に必ず確認する）**:
- Zabbix管理画面で該当プロキシが「Available」表示になっている
- 発行された **`proxyid`**（Zabbix Proxy ID）をワークシートの**proxyid列（Y列）**に貼り付けている（`Sensor Edge/実施手順_顧客追加フロー.md`手順5-7の「右クリック→検証（Inspect）→`data-proxyid`属性を読む」の方法で調べる。手順2で使う）

> **重要な順序**: この手順1を完了させてから、次の手順2（オンボーディングスクリプト）を実行すること。**逆の順番で実行すると、後から直すのに手作業のデータベース修正が必要になる**ため、順番を守ること。

## 手順2: ポータルへの顧客登録

1. **画面/コマンド**: 以下を実行し、`msp-frontend-server`にSSH接続する（`npm run onboard`は本番の認証情報・DB接続がセットアップ済みのこのサーバー上でのみ実行できる）
   ```bash
   gcloud compute ssh msp-frontend-server --zone=asia-northeast1-a --tunnel-through-iap
   ```
2. **操作**: 接続後、以下でプロジェクトのディレクトリへ移動する
   ```bash
   cd /opt/atlib-msp-dev/msp-customer-portal
   ```
3. **操作**: [Sensor Edge 機器管理台帳](https://docs.google.com/spreadsheets/d/1x5dtPGwh-AqJamPmKA8TTj40D9noYWancf7WipK5I4E/edit)の「顧客追加ワークシート」タブを開き、該当行の**「【手順2(portal)】npm run onboardコマンド」列（Z列）**の内容をそのままコピーして実行する（顧客ID・会社名・メールアドレス・proxyid・IPレンジがすべて自動で埋め込まれている。空欄がある場合は`⚠`と表示されるので、その場合は先に該当列を埋める。プラン名は契約管理用の参考情報であり、このコマンドには含まれない）
4. **確認**: エラーなく完了すること。`customer_code`が既に使われている場合はエラーで止まる（別のコードを使う）
5. **確認**: 完了時にコンソールに次の手順3でそのまま使うコマンドが表示されるので、そのままコピーしておく
6. **確認**: 手順0で顧客マスタへの割当を済ませているはずだが、まだの場合はここで必ず行う（忘れると、Sensor Edge機器登録フォームの顧客IDプルダウンにこの顧客が出てこない）

## 手順3: 機器の自動検出を設定する

1. **画面/コマンド**: 以下を実行し、`msp-frontend-server`にSSH接続する
   ```bash
   gcloud compute ssh msp-frontend-server --zone=asia-northeast1-a --tunnel-through-iap
   ```
2. **操作**: 接続後、以下を実行する
   ```bash
   cd /opt/atlib-msp-dev/zabbixserver/batch
   ```
3. **操作**: 接続情報を読み込む（`~/zabbix_env.sh`が無い場合は、この手順書の一番上「作業者の初回セットアップ」を先に実施する）
   ```bash
   source ~/zabbix_env.sh
   ```
4. **操作**: まず内容確認のため、手順2で表示されたコマンドの`--dry-run`版を実行する（`python`ではなく**`python3`**）
   ```bash
   python3 setup_discovery.py --dry-run --customer-code <code> --company-name "<name>"
   ```
5. **確認**: 3つのアクションが「作成済み」と表示されること
6. **操作**: 問題なければ、手順2の出力にあった`--apply`のコマンドをそのまま貼り付けて実行する（先頭を`python`から`python3`に書き換える）
7. **注意**: この手順はCloud Run（本番アプリ本体）からは実行できない。必ず`msp-frontend-server`にSSHした状態で実行すること

---

## 手順4: 顧客への引き渡し

- **操作**: 歓迎メール（手順2で自動送信済み）が実際に顧客に届いているか確認する
- **操作**: 顧客に以下を案内する
  - ログインURL: ポータルの `/login.html`
  - パスワードを忘れた場合: `/reset-password.html` から再設定できる
  - 「未知機器の検出」通知トグル（通知設定ページ、デフォルト無効）について案内する
  - 「トポロジー」画面（`/topology.html`）を案内する。機器の役割（ルーター/スイッチ/AP/プリンター等）や、上位接続先・ケーブル種別を顧客自身で設定できること、月次報告書にも同じ内容が反映されることを伝える

---

## 手順5: 監視が始まっていることの確認

1. **画面**: ポータルの「機器管理」画面を開く
2. **確認**: 手順3で設定した機器が自動的に一覧表示されていること
3. 不要な機器がある場合、顧客はポータルから無効化・削除できる
4. **注意（顧客への案内事項）**: 機器を「削除」しても、その機器が引き続き稼働していると次回の自動検出で再登録されることがある。恒久的に監視を止めたい場合は「削除」ではなく「無効化」を使うよう顧客に案内する

## 手順6: 契約終了時の後処理

Sensor Edge側（機器回収・認証情報の失効）は `Sensor Edge/実施手順_顧客追加フロー.md` の手順10を参照。ここでは**ポータル側**の後処理のみ扱う。

### 6-1. ポータルへのログインを止める

**注意**: これは顧客の実データを直接書き換える操作。実施前に必ず関係者の承認を得ること。

1. **画面/コマンド**: `msp-frontend-server`にSSH接続する
   ```
   gcloud compute ssh msp-frontend-server --zone=asia-northeast1-a --tunnel-through-iap
   ```
2. **操作**: 接続後、以下を実行する（Cloud SQL Auth Proxyは`cloud-sql-proxy.service`として常駐済みのため、追加の起動操作は不要）
   ```bash
   cd /opt/atlib-msp-dev/msp-customer-portal
   set -a; source .env; set +a
   ```
3. **操作**: 以下を実行する。SQL文はワークシートの**「【契約終了】ポータル停止SQLコマンド」列**に自動生成されているので、そのままコピーして`-c`の後ろ（ダブルクォートで囲んだ部分）に貼り付ける
   ```bash
   PGPASSWORD="$DB_PASSWORD" psql -h "$DB_HOST" -p "$DB_PORT" -U "$DB_USER" -d "$DB_NAME" -c "UPDATE customers SET status = 'suspended', updated_at = now() WHERE customer_code = '<対象customer_code>';"
   ```
4. **確認**: `UPDATE 1`と表示されること（0件の場合は`customer_code`が間違っている）。この更新だけで、顧客は即座にログイン・API利用ができなくなる（アプリ側の変更は不要）

### 6-2. Zabbix側は「削除」ではなく「無効化」から始める

**まず無効化のみ行う（削除はしない）**。以下は好きな順でよい（依存関係なし）。

1. **画面**: Zabbix管理画面で、以下をすべて**無効化**する（削除はまだしない）
   - 該当顧客のディスカバリアクション3件（`MSP_SNMP機器登録_{code}`・`MSP_ICMPフォールバック登録_{code}`・`MSP_新規機器検知通知_{code}`）
   - 該当顧客のディスカバリルール（`MSP_インフラ自動検知_{code}`）
   - 顧客専用アクション（`{code}_alert`）
   - 通知用Zabbixユーザー（`notify_{code}`）
   - 該当顧客のホストグループに属する全ホスト

保持期間（目安1〜3ヶ月、契約内容による）が経過し、削除してよいと判断した場合のみ、以下の順序で削除する（**この順序は必須**。逆順にすると「ホストが残っているためホストグループを削除できない」というエラーになる）。

2. **削除する場合（担当エンジニアと相談の上で実施）**: 上記と同じ5項目を、以下の順に削除する
   1. ディスカバリアクション3件
   2. ディスカバリルール
   3. 顧客専用アクション（`{code}_alert`）
   4. 通知用Zabbixユーザー（`notify_{code}`）
   5. ホストグループ内の全ホスト
   6. ホストグループ本体（**必ず5の後**）

### 6-3. データの保持

ポータルDBのレコードは`suspended`のまま一定期間保持し、その後の削除要否は担当エンジニアに確認する。

## うまくいかない場合

### `npm run onboard` の後、顧客がログインできない

- 歓迎メールが迷惑メールフォルダに入っていないか、顧客に確認してもらう
- それでも解決しない場合は担当エンジニアに連絡する

### 機器管理画面に自動登録された機器が表示されない

- 手順3を実行し忘れていないか確認する
- 入力した`--ip-range`が顧客の実際のネットワークと合っているか確認する
- 解決しない場合は担当エンジニアに連絡する

### 手順1より先に手順2を実行してしまった

- 自分では直せない。すぐに担当エンジニアに連絡する（手作業でのデータベース修正が必要）
