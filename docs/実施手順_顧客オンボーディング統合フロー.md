# 実施手順（かんたん版）: 顧客オンボーディング統合フロー

最終更新: 2026-07-21
対応する詳細仕様書: `msp-customer-portal/docs/運用手順書_顧客オンボーディング統合フロー.md`

## これは何の作業か

申込みが確定した顧客を、実際に監視サービスが使える状態にするまでの一連の作業。Sensor Edge（拠点設置の機器）の設置と、顧客ポータル（Webサイト）への登録の両方を行う。

## 始める前に

以下がヒアリング（Web会議）で確定していること。無ければ担当者に確認してから始める。

| 項目 | 例 |
|---|---|
| `customer_code`（英数字ID） | `atlse000003`のような形式（`atlse`＋6桁連番）。自分で決めず、手順0で顧客マスタから割り当てる |
| `company_name`（正式名称） | `atLIB株式会社様` |
| 連絡先メールアドレス | |
| プラン名 | `エントリープラン` |
| 顧客のネットワークのIPレンジ | `192.168.1.1-254` |
| SNMP監視対象機器のおおよその台数 | 50台が目安の上限。超えそうな場合は担当エンジニアに相談 |

また、`msp-frontend-server`にSSH接続できる環境が必要（手順3で使用）。

---

## 手順0: 顧客マスタで顧客IDを割り当てる（手順1より先に実施）

1. **画面**: [Sensor Edge 機器管理台帳](https://docs.google.com/spreadsheets/d/1x5dtPGwh-AqJamPmKA8TTj40D9noYWancf7WipK5I4E/edit)を開き、「顧客マスタ」タブを開く
2. **操作**: 「顧客名」欄が**空欄**になっている行のうち、一番上の行を選ぶ（空欄＝未割当の顧客ID）
3. **操作**: その行の「顧客名」欄に会社名（`company_name`）を記入する。連絡先メールアドレス・備考も分かれば記入する
4. **確認**: その行の「顧客ID」の値（例: `atlse000003`）を控える。これが以降の手順で使う`customer_code`になる（「顧客名」欄が埋まった時点でこの顧客IDは割当済み扱いになる。ステータス列は存在しない）
5. **注意**: この手順を飛ばして手順1に進むと、Sensor Edge機器登録フォームの顧客IDプルダウンにこの顧客が出てこず、機器を登録できない

---

## 手順1: Sensor Edgeの設置（全顧客で必ず実施）

この手順は省略できない。**必ず** `Sensor Edge/実施手順_顧客追加フロー.md` の手順1〜9をそのまま実施する。

**完了条件（次の手順に進む前に必ず確認する）**:
- Zabbix管理画面で該当プロキシが「Available」表示になっている
- 発行された **`proxyid`**（Zabbix Proxy ID）をワークシートの**proxyid列（Y列）**に貼り付けている（`Sensor Edge/実施手順_顧客追加フロー.md`手順5-7の「右クリック→リンクのアドレスをコピー」の方法で調べる。手順2で使う）

> **重要な順序**: この手順1を完了させてから、次の手順2（オンボーディングスクリプト）を実行すること。**逆の順番で実行すると、後から直すのに手作業のデータベース修正が必要になる**ため、順番を守ること。

---

## 手順2: ポータルへの顧客登録

1. **画面/コマンド**: 以下を実行し、`msp-frontend-server`にSSH接続する（`npm run onboard`は本番の認証情報・DB接続がセットアップ済みのこのサーバー上でのみ実行できる）
   ```bash
   gcloud compute ssh msp-frontend-server --zone=asia-northeast1-a --tunnel-through-iap
   ```
2. **操作**: 接続後、以下でプロジェクトのディレクトリへ移動する
   ```bash
   cd /opt/atlib-msp-dev/msp-customer-portal
   ```
3. **操作**: [Sensor Edge 機器管理台帳](https://docs.google.com/spreadsheets/d/1x5dtPGwh-AqJamPmKA8TTj40D9noYWancf7WipK5I4E/edit)の「顧客追加ワークシート」タブを開き、該当行の**「【手順2(portal)】npm run onboardコマンド」列（Z列）**の内容をそのままコピーして実行する（顧客ID・会社名・メールアドレス・プラン名・proxyid・IPレンジがすべて自動で埋め込まれている。空欄がある場合は`⚠`と表示されるので、その場合は先に該当列を埋める）
4. **確認**: エラーなく完了すること。`customer_code`が既に使われている場合はエラーで止まる（別のコードを使う）
5. **確認**: 完了時にコンソールに次の手順3でそのまま使うコマンドが表示されるので、そのままコピーしておく
6. **確認**: 手順0で顧客マスタへの割当を済ませているはずだが、まだの場合はここで必ず行う（忘れると、Sensor Edge機器登録フォームの顧客IDプルダウンにこの顧客が出てこない）

---

## 手順3: 機器の自動検出を設定する

1. **画面/コマンド**: 以下を実行し、`msp-frontend-server`にSSH接続する
   ```bash
   gcloud compute ssh msp-frontend-server --zone=asia-northeast1-a --tunnel-through-iap
   ```
2. **操作**: 接続後、以下を実行する
   ```bash
   cd /opt/atlib-msp-dev/zabbixserver/batch
   ```
3. **操作**: まず内容確認のため、手順2で表示されたコマンドの`--dry-run`版を実行する
   ```bash
   python setup_discovery.py --dry-run --customer-code <code> --company-name "<name>"
   ```
4. **確認**: 3つのアクションが「作成済み」と表示されること
5. **操作**: 問題なければ、手順2の出力にあった`--apply`のコマンドをそのまま貼り付けて実行する
6. **注意**: この手順はCloud Run（本番アプリ本体）からは実行できない。必ず`msp-frontend-server`にSSHした状態で実行すること

---

## 手順4: 顧客への引き渡し

- **操作**: 歓迎メール（手順2で自動送信済み）が実際に顧客に届いているか確認する
- **操作**: 顧客に以下を案内する
  - ログインURL: ポータルの `/login.html`
  - パスワードを忘れた場合: `/reset-password.html` から再設定できる
  - 「未知機器の検出」通知トグル（通知設定ページ、デフォルト無効）について案内する
  - 「トポロジー」画面（`/topology.html`）を案内する。機器の役割（ルーター/スイッチ/AP/プリンター等）や、上位接続先・ケーブル種別を顧客自身で設定できること、月次報告書にも同じ内容が反映されることを伝える

---

## 手順5: 監視が始まっていることの確認

1. **画面**: ポータルの「機器管理」画面を開く
2. **確認**: 手順3で設定した機器が自動的に一覧表示されていること
3. 不要な機器がある場合、顧客はポータルから無効化・削除できる
4. **注意（顧客への案内事項）**: 機器を「削除」しても、その機器が引き続き稼働していると次回の自動検出で再登録されることがある。恒久的に監視を止めたい場合は「削除」ではなく「無効化」を使うよう顧客に案内する

---

## 手順11: 契約終了時の後処理

Sensor Edge側（機器回収・認証情報の失効）は `Sensor Edge/実施手順_顧客追加フロー.md` の手順10を参照。ここでは**ポータル側**の後処理のみ扱う。

### 11-1. ポータルへのログインを止める

**注意**: これは顧客の実データを直接書き換える操作。実施前に必ず関係者の承認を得ること。

1. **画面/コマンド**: Cloud SQL Auth Proxy経由で`msp-customer-portal-db`に接続する（接続方法が分からない場合は担当エンジニアに確認）
2. **操作**: 以下のSQLを実行する（`<対象customer_code>`を実際の値に書き換える）
   ```sql
   UPDATE customers SET status = 'suspended', updated_at = now() WHERE customer_code = '<対象customer_code>';
   ```
3. **確認**: この更新だけで、顧客は即座にログイン・API利用ができなくなる（アプリ側の変更は不要）

### 11-2. Zabbix側は「削除」ではなく「無効化」から始める

1. **画面**: Zabbix管理画面で、該当顧客のホストグループに属する全ホストを**無効化**する（削除はしない）
2. **操作**: 通知用Zabbixユーザー（`notify_{customer_code}`）・顧客専用アクションも同様に無効化する
3. 保持期間（目安1〜3ヶ月、契約内容による）が経過し、問題なければホストグループごと削除する（削除は担当エンジニアと相談の上で実施）

### 11-3. データの保持

ポータルDBのレコードは`suspended`のまま一定期間保持し、その後の削除要否は担当エンジニアに確認する。

## うまくいかない場合

### `npm run onboard` の後、顧客がログインできない

- 歓迎メールが迷惑メールフォルダに入っていないか、顧客に確認してもらう
- それでも解決しない場合は担当エンジニアに連絡する

### 機器管理画面に自動登録された機器が表示されない

- 手順3を実行し忘れていないか確認する
- 入力した`--ip-range`が顧客の実際のネットワークと合っているか確認する
- 解決しない場合は担当エンジニアに連絡する

### 手順1より先に手順2を実行してしまった

- 自分では直せない。すぐに担当エンジニアに連絡する（手作業でのデータベース修正が必要）
